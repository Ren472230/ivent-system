# IVENT SYSTEM – архитектурная спецификация

Дата: 2026-09-15
Статус: на утверждение
Целевой первый релиз: 0.1 Party Core (ядро вечеринки, дословно «ядро вечеринки»)

## 1. Назначение

IVENT SYSTEM – модульная система проведения домашних мероприятий, дней рождения и игровых вечеров. Система объединяет несколько простых игр в единый сценарий, сохраняет общее состояние между этапами и позволяет постепенно добавлять ИИ-механики без переписывания базового ядра.

Главный принцип продукта: участники приходят играть, а возможности ИИ проявляются внутри игровых механик. Отдельный «чат с нейросетью» не является центром опыта.

## 2. Цели первого релиза

Версия 0.1 должна позволять одному ведущему провести полноценный вечер с одного компьютера от создания мероприятия до итогового экрана.

Обязательные возможности:

- создание мероприятия;
- регистрация игроков;
- последовательность этапов и перерывов;
- таймер этапа;
- жетоны;
- магазин;
- предметы и активируемые эффекты;
- инвентарь игроков;
- журнал действий;
- отмена последнего безопасно обратимого действия;
- локальное сохранение;
- экспорт и импорт сохранения;
- три ячейки сохранения;
- резервная копия сохранения;
- пять проверенных офлайн-игр как сценарные модули;
- аукцион артефактов как первая новая игра;
- итоговая статистика вечера.

## 3. Границы версии 0.1

В первую версию сознательно не входят:

- аккаунты пользователей;
- постоянный сервер;
- облачная база данных;
- многопользовательский вход с телефонов;
- сетевой режим;
- собственная модель ИИ;
- сложный редактор игр;
- платежи;
- публичный каталог пользовательских сценариев.

ИИ-игры проектируются архитектурно, но их подключение идёт после стабилизации ядра.

## 4. Принципы проектирования

### 4.1. Один файл для запуска

Первый рабочий формат – один автономный HTML-файл с встроенными стилями и логикой. Его можно открыть локально в браузере без сервера.

Разработка внутри репозитория может использовать раздельные исходные модули и автоматическую сборку в один конечный HTML-файл. Пользовательский артефакт версии 0.1 остаётся одним файлом.

### 4.2. Модульность

Каждый модуль отвечает только за одну область:

1. ядро мероприятия;
2. игроки;
3. экономика;
4. предметы и эффекты;
5. игровые модули;
6. ИИ-адаптеры;
7. интерфейс ведущего;
8. журнал и хроника;
9. сохранения.

Модули взаимодействуют через явные команды и события. Игровой модуль не меняет состояние жетонов или инвентаря напрямую.

### 4.3. Детерминированность

Одинаковое исходное состояние и одинаковая последовательность команд должны приводить к одинаковому состоянию системы, кроме специально помеченных случайных операций.

Все случайные операции получают сохраняемое начальное значение генератора случайности, чтобы результат можно было воспроизвести при отладке.

### 4.4. Обратимость

Все операции, для которых предусмотрена отмена, обязаны хранить достаточно данных для корректного восстановления предыдущего состояния.

### 4.5. Отсутствие скрытых изменений

Любое изменение жетонов, инвентаря, результата этапа или активного предмета записывается в журнал.

## 5. Базовые параметры мероприятия

Параметры хранятся в конфигурации конкретного вечера.

| Параметр | По умолчанию | Допустимое значение |
|---|---:|---:|
| Количество игроков | 6 | 3–30 |
| Количество команд | 0 | 0–6 |
| Длительность вечера | 240 минут | 120–480 минут |
| Количество игровых этапов | 6 | 3–12 |
| Количество перерывов | 2 | 0–4 |
| Длительность этапа | 20 минут | 5–45 минут |
| Стартовые жетоны | 5 | 0–20 |
| Максимум активных предметов | 1 | 1–3 |
| Физические призы | 10 | 0–30 |
| Автосохранение | включено | включено / выключено |
| Журналирование | включено | всегда включено |

Ограничения являются значениями интерфейса версии 0.1, а не фундаментальными техническими пределами.

## 6. Состояния мероприятия

Состояние мероприятия хранится явно.

Допустимые состояния:

- PREPARATION – подготовка;
- LOBBY – сбор игроков;
- PLAYING – активный этап;
- BREAK – перерыв;
- RESULT – результаты этапа;
- FINISHED – мероприятие завершено.

Допустимые переходы:

PREPARATION → LOBBY → PLAYING → RESULT → PLAYING

PLAYING → BREAK → PLAYING

RESULT → FINISHED

Возврат к предыдущему состоянию допускается только через отдельную административную команду ведущего и обязательно журналируется.

## 8. Командно-событийная модель

Изменения состояния выполняются командами.

Примеры команд:

- CREATE_EVENT;
- ADD_PLAYER;
- UPDATE_PLAYER;
- START_STAGE;
- PAUSE_STAGE;
- FINISH_STAGE;
- AWARD_TOKENS;
- SPEND_TOKENS;
- TRANSFER_TOKENS;
- BUY_ITEM;
- GIVE_ITEM;
- ACTIVATE_ITEM;
- DEACTIVATE_ITEM;
- APPLY_EFFECT;
- UNDO_LAST_ACTION.

После успешной команды создаётся событие журнала.

Примеры событий:

- PLAYER_ADDED;
- TOKENS_AWARDED;
- ITEM_PURCHASED;
- ITEM_ACTIVATED;
- STAGE_STARTED;
- STAGE_FINISHED;
- ACTION_UNDONE.

Команда проходит этапы:

1. валидация;
2. вычисление результата;
3. изменение состояния;
4. создание записи журнала;
5. автосохранение;
6. обновление интерфейса.

Если валидация не пройдена, состояние не изменяется.

## 9. Экономика

### 9.1. Источники жетонов

- стартовый баланс;
- победа;
- место в этапе;
- персональное достижение;
- специальное событие;
- продажа разрешённого предмета;
- ручная награда ведущего.

### 9.2. Расходы

- магазин;
- аукцион;
- ставка;
- активация платной способности;
- покупка информации;
- игровой штраф.

### 9.3. Базовые ориентиры баланса

Цель: к финалу средний игрок должен потратить 60–90% всех заработанных жетонов.

Средняя стоимость предмета ориентировочно составляет 20–35% ожидаемого дохода игрока за вечер.

Эти значения являются настройками баланса, а не жёсткими ограничениями движка.

### 9.4. Инварианты экономики

- каждая операция имеет источник и причину;
- каждая операция записывается в журнал;
- сумма списания должна быть положительной;
- при выключенном разрешении долгов баланс не может стать ниже нуля;
- покупка и передача предмета являются атомарными операциями;
- отмена покупки восстанавливает и баланс, и владельца предмета.

## 10. Система предметов и эффектов

Главная цель предметов – создавать заметные игровые события.

Предпочтительные категории:

- защита;
- атака;
- информация;
- изменение правил;
- экономика;
- саботаж;
- перенаправление;
- кража;
- усиление;
- управление порядком действий.

Слабые пассивные эффекты вида «+1 жетон после этапа» допускаются только как дешёвые обычные предметы.

### 10.1. Окна активации

- BEFORE_STAGE – до этапа;
- DURING_STAGE – во время этапа;
- BEFORE_RESULT – до объявления результата;
- AFTER_RESULT – после результата;
- ANYTIME – в любое допустимое время;
- MANUAL_ONLY – только вручную ведущим.

### 10.2. Цели эффекта

- SELF – владелец;
- ONE_PLAYER – один другой игрок;
- ANY_PLAYER – любой игрок;
- TWO_PLAYERS – два игрока;
- TEAM – команда;
- ALL – все участники;
- STAGE – текущий этап.

### 10.3. Ограничение активных предметов

По умолчанию у игрока одновременно активен один предмет. Ограничение настраивается на уровне мероприятия.

## 11. Игровой движок

Игровой модуль обязан реализовывать следующие операции:

- initialize(config, context);
- start();
- pause();
- resume();
- handleCommand(command);
- getPublicState();
- getHostState();
- finish();
- getResult();
- serialize();
- restore(serializedState).

Игровой модуль получает ограниченный контекст ядра и отправляет наружу команды. Прямой доступ к глобальному хранилищу запрещён.

### 11.1. Критерий модульности

Новую мини-игру можно добавить без изменения ядра, экономики и системы сохранений.

## 12. Игры версии 0.1

### 12.1. Проверенные сценарные модули

- Элиас;
- Уно;
- Дурак;
- Пиковая дама;
- Солнышко.

Для этих игр приложение версии 0.1 выступает прежде всего как ведущий, таймер, счётчик наград и журнал. Полная цифровая реализация карточной механики не требуется.

### 12.2. Аукцион артефактов

Это первая полностью встроенная новая игра.

Параметры:

- 3–10 лотов;
- стартовая цена 1–10 жетонов;
- шаг ставки 1–5 жетонов;
- таймер лота 20–60 секунд;
- открытый или скрытый эффект;
- ручное или автоматическое завершение ставки;
- возможность запрета ставки самому себе не применяется, так как игроки конкурируют за общий лот.

Критерии завершения лота:

- истёк таймер и есть лидер;
- ведущий завершил торги вручную;
- все кроме лидера отказались.

Покупка должна быть атомарной: списание жетонов и передача предмета происходят одной операцией.

## 13. ИИ-слой

ИИ не встраивается напрямую в игровые модули.

Игры обращаются к абстрактному интерфейсу возможностей:

- generateCharacter;
- converseAsCharacter;
- judgeResponse;
- generateChallenge;
- generateImage;
- summarizeEvent;
- generateAward.

Поставщик модели подключается отдельно.

### 13.1. Режим без ИИ

Любая ИИ-игра должна иметь понятное состояние ошибки и позволять ведущему:

- повторить запрос;
- ввести результат вручную;
- пропустить ИИ-операцию;
- завершить этап без потери общего состояния.

### 14.1. ИИ-босс

Параметры персонажа:

- имя;
- характер;
- цель;
- слабость;
- секрет;
- упрямство 1–10;

- условия поражения.

### 14.2. Суд

Параметры:

- длительность речи 30–120 секунд;

- свидетели включены / выключены;

### 14.3. Каракуля

Параметры:

- время рисования 30–120 секунд;
- тема;
- число вариантов результата 1–4;
- публичное голосование включено / выключено;
- награда за победу 1–10 жетонов.

## 15. Интерфейс ведущего

Главный экран разделён на четыре смысловые области:

1. текущий этап;
2. игроки и балансы;
3. журнал последних событий;
4. основные действия ведущего.

Приоритет информации:

- самый крупный блок – текущий этап и таймер;
- средний – игроки, жетоны, активные предметы;
- компактный – история и административные действия.

### 15.1. Обязательные действия ведущего

- добавить / удалить игрока до старта;
- изменить жетоны;
- выдать предмет;
- активировать / деактивировать предмет;
- завершить этап;
- пропустить этап;
- вставить перерыв;
- открыть магазин;
- открыть аукцион;
- отменить последнюю обратимую операцию;
- сохранить вручную;
- экспортировать состояние.

### 15.2. Защита от случайных действий

Подтверждение требуется для:

- удаления игрока после начала мероприятия;
- полного сброса сохранения;
- завершения всего мероприятия;
- удаления предмета;
- импорта сохранения поверх активной игры.

Обычные операции с жетонами подтверждения не требуют, поскольку доступны через отмену.

## 16. Журнал и хроника

Каждая запись журнала содержит:

- id;
- timestamp;
- type;
- actorId;
- targetIds;
- stageId;
- payload;
- reversible;
- inverseCommand;
- humanReadableText.

Журнал используется одновременно для:

- истории действий;
- отладки;
- отмены;
- итоговой статистики;
- будущей генерации хроники вечера.

## 17. Отмена действий

Версия 0.1 поддерживает линейную отмену последнего обратимого пользовательского действия.

Обратимы:

- начисление и списание жетонов;
- покупка предмета;
- ручная передача предмета;
- активация / деактивация простого предмета;
- изменение результата этапа до перехода к следующему этапу.

Не считаются автоматически обратимыми:

- внешняя ИИ-генерация;
- физическая выдача приза;
- действия, уже повлиявшие на реальную карточную игру;
- импорт сохранения.

Для таких случаев ведущий получает ручные корректирующие действия.

## 18. Сохранение

### 18.1. Ячейки

Три независимые ячейки.

Каждая содержит:

- основное состояние;
- резервную копию предыдущего валидного состояния;
- контрольную сумму;
- версию схемы;
- время последней записи.

### 18.2. Автосохранение

Автосохранение выполняется после каждой успешной изменяющей команды.

### 18.3. Повреждение данных

При невозможности разобрать основное сохранение система предлагает восстановить резервную копию.

### 18.4. Экспорт и импорт

Экспорт создаёт JSON-файл.

Импорт выполняет:

1. разбор JSON;
2. проверку версии;
3. миграцию при наличии поддерживаемого пути;
4. валидацию структуры;
5. создание резервной копии текущего состояния;
6. замену активного состояния.

## 19. Версионирование и миграции

Каждое сохранение содержит schemaVersion.

Правила:

- новая версия приложения обязана читать текущую схему;
- поддержка старых схем обеспечивается миграциями;
- неизвестная более новая схема не загружается молча;
- миграция не изменяет исходный экспорт пользователя;
- каждая миграция тестируется отдельным набором данных.

## 20. Обработка ошибок

Ошибки делятся на категории:

- VALIDATION – недопустимое действие;
- STORAGE – проблема сохранения;
- MODULE – ошибка игры;
- AI_PROVIDER – ошибка внешней модели;
- IMPORT – некорректный файл;
- INTERNAL – непредвиденное состояние.

Для VALIDATION интерфейс показывает понятную причину и сохраняет текущее состояние без изменений.

Для STORAGE система пытается сохранить резервную копию в независимый ключ локального хранилища.

Для MODULE текущий этап можно аварийно завершить или пропустить без повреждения мероприятия.

## 21. Тестовая стратегия

### 21.1. Модульные проверки

Обязательны для:

- экономики;
- магазина;
- покупки предметов;
- передачи предметов;
- активации эффектов;
- переходов состояния;
- сериализации;
- миграций;
- отмены операций;
- аукциона.

### 21.2. Сценарные проверки

Минимальные сценарии:

1. создать мероприятие → добавить 5 игроков → провести 3 этапа → завершить;
2. купить предмет → активировать → отменить;
3. сохранить → перезапустить → восстановить;
4. повредить основное сохранение → восстановить резервное;
5. экспортировать → сбросить → импортировать;
6. провести полный аукцион с несколькими ставками;
7. закончить вечер и получить корректную статистику.

### 21.3. Проверка интерфейса

Для ключевых экранов проверяются:

- ширина 1280×720;
- ширина 1920×1080;
- отсутствие горизонтальной прокрутки;
- видимость основных кнопок;
- читаемость с расстояния около 2–3 метров на общем экране.

## 22. Метрики качества игрового модуля

Каждая новая игра оценивается по пяти показателям:

| Показатель | Цель |
|---|---:|
| Объяснение правил | до 2 минут |
| Подготовка | до 3 минут |
| Продолжительность | 5–20 минут |
| Ручные действия ведущего | минимальны |
| Повторное использование | минимум 3 разных сценария |

Если игра систематически нарушает три и более цели, её нужно упрощать до включения в основной набор.

## 26. Основные риски

### Риск 1. Один HTML-файл станет слишком большим

Снижение риска: исходники остаются модульными, единый файл является только результатом сборки.

### Риск 2. Система эффектов станет слишком универсальной и сложной

Снижение риска: версия 0.1 поддерживает ограниченный набор типов эффектов. Новый тип добавляется только под реальную игру или предмет.

### Риск 3. ИИ-операции будут нестабильны

Снижение риска: ИИ отделён от ядра и всегда имеет ручной резервный путь.

### Риск 4. Ведущий будет слишком много нажимать

Снижение риска: каждая основная операция проектируется под 2–3 действия, а повторяющиеся операции получают быстрые кнопки.

### Риск 5. Потеря прогресса во время вечеринки

Снижение риска: автосохранение после каждой команды, резервная копия, три ячейки и экспорт.

## 27. Архитектурные решения, зафиксированные этой спецификацией

1. Первый пользовательский артефакт – автономный HTML-файл.
2. Исходный код может быть модульным и собираться автоматически.
3. Ядро работает без ИИ и без интернета.
4. Игры не управляют глобальным состоянием напрямую.
5. Экономика централизована.
6. Все важные изменения проходят через команды и журнал.
7. Сохранение является частью ядра, а не дополнительной функцией.
8. Аукцион – первая новая полностью цифровая игра.
9. Старые карточные игры в 0.1 представлены как сценарные модули ведущего.
10. Телефоны игроков и серверный режим откладываются до отдельной крупной версии.

## 28. Определение успеха

Первая версия успешна, если ведущий может открыть один файл, создать вечер, добавить участников, провести последовательность игр с жетонами и предметами, восстановиться после перезапуска, завершить мероприятие и показать итоговую статистику без ручного вмешательства в исходный код или внутренние данные.
