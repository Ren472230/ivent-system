# IVENT SYSTEM 0.2 – Game Library Design

Дата: 2026-09-15
Статус: утверждено пользователем для автономной реализации
База: `feat/party-core-v01-impl`

## 1. Цель

Превратить жёсткий список игр версии 0.1 в управляемую библиотеку. Ведущий должен уметь активировать и архивировать игры, создавать новую игру прямо во время вечера, добавлять её как этап, хранить изображение и полный паспорт правил.

## 2. Главный принцип

Игра – это шаблон. Этап – конкретное использование шаблона в конкретном мероприятии.

Архивирование игры влияет только на дальнейший выбор игры. Уже созданные этапы продолжают работать.

Пользовательские игровые модули считаются неизменяемыми версиями. Редактирование создаёт новую версию с новым `moduleId`, поэтому уже созданные этапы сохраняют исходные правила.

## 3. Game Manifest

Каждая игра имеет паспорт со следующими полями:

- `moduleId` – неизменяемый технический идентификатор версии;
- `gameId` – постоянный идентификатор логической игры;
- `revision` – номер редакции;
- `name` – короткое название;
- `summary` – суть игры в одном предложении;
- `rules` – полные правила;
- `goal` – цель игрока или команды;
- `minPlayers`, `maxPlayers`;
- `estimatedMinutes`;
- `mode` – individual / teams / mixed / system;
- `resultMode` – способ фиксации результата;
- `defaultWinnerReward`;
- `itemsPolicy` – allowed / before-after / forbidden;
- `aiCapabilities` – перечень возможностей ИИ;
- `requiredProps` – реквизит;
- `hostNotes` – заметки ведущему;
- `tags` – категории;
- `cover` – обложка;
- `source` – system / custom;
- `active` – доступна ли игра для добавления новых этапов;
- `createdAt`, `updatedAt`;
- `supersedesModuleId` – предыдущая версия при редактировании.

## 4. Обложка

Целевой формат – 16:9, рабочий размер 800×450.

Пользовательская картинка:

1. выбирается локальным файлом;
2. обрезается по центру под 16:9;
3. уменьшается до 800×450;
4. сохраняется как JPEG или WebP с целевым размером около 150 КБ;
5. хранится как data URL внутри библиотеки.

Если изображение не загружено, система создаёт встроенную SVG-обложку с названием и визуальным символом. Внешняя сеть для обложек не требуется.

## 5. Состояния игры

- `active=true` – показывается в обычной библиотеке и в выборе нового этапа;
- `active=false` – находится в архиве;
- архивирование не удаляет данные;
- восстановление из архива снова разрешает добавлять игру;
- системные игры можно архивировать и восстанавливать;
- системные игры не редактируются напрямую: действие «Дублировать» создаёт пользовательскую копию;
- пользовательская игра редактируется созданием новой версии.

## 6. Экран «Игры»

В навигации появляется раздел «Игры».

Экран содержит:

- кнопку `+ Создать игру`;
- вкладки / блоки «Активные» и «Архив»;
- карточки 16:9;
- название, краткую суть, число игроков, длительность, реквизит и ИИ-маркер;
- действия: `Добавить этап`, `Паспорт`, `Дублировать`, `В архив` / `Вернуть`;
- для пользовательской игры дополнительно `Редактировать`.

## 7. Быстрое создание

Из экрана программы рядом с добавлением этапа появляется `+ Новая игра`.

Минимально обязательные поля:

- название;
- краткая суть или правила;
- длительность;
- режим результата;
- награда.

После сохранения можно сразу создать этап. Новая игра одновременно сохраняется в библиотеку.

## 8. Полный редактор

Редактор позволяет задать весь Game Manifest.

Поля сгруппированы:

1. Образ – название, обложка, суть;
2. Правила – цель, подробные правила, заметки ведущему;
3. Параметры – игроки, время, формат, результат;
4. Экономика – награда и предметы;
5. Реквизит;
6. ИИ-возможности;
7. Теги.

## 9. Совместимость с ядром 0.1

Версия 0.2 не переписывает командное ядро. Пользовательская игра регистрируется через существующий `registerGameModule()` и после регистрации может использовать существующую команду `ADD_STAGE`.

Архивирование фильтрует доступность игры для новых `ADD_STAGE`, при этом модуль остаётся зарегистрированным в рантайме для уже существующих этапов.

## 10. Снимок игры в этапе

Для версии 0.2 применяется неизменяемая версионность модулей:

- каждый `moduleId` представляет конкретную редакцию паспорта;
- редактирование пользовательской игры создаёт новый `moduleId`;
- старый `moduleId` сохраняется и скрывается как историческая версия;
- этап хранит старый `moduleId`, поэтому его правила остаются прежними.

Это даёт поведение снимка без миграции структуры `Stage` версии 0.1.

## 11. Хранение и перенос

Библиотека хранится локально отдельным ключом версии 0.2.

Адаптер сохранений оборачивается так, чтобы экспорт мероприятия версии 0.2 содержал:

- состояние мероприятия;
- библиотеку игр.

Импорт пакета версии 0.2 восстанавливает оба блока. Импорт обычного сохранения версии 0.1 продолжает поддерживаться.

## 12. Ограничения

- одна пользовательская обложка после обработки должна стремиться к размеру ≤150 КБ;
- система должна работать без интернета;
- библиотека должна запускаться из одного итогового HTML-файла;
- архивная игра не должна появляться в селекторе добавления этапа;
- существующий этап архивной игры должен отображаться и завершаться штатно;
- новая игра должна создаваться без перезагрузки страницы;
- пользователь может быстро создать игру минимум из названия, правил, времени, результата и награды.

## 13. Критерии готовности 0.2

1. В интерфейсе есть раздел «Игры».
2. Все встроенные игры имеют визуальные карточки.
3. Игру можно архивировать и восстановить.
4. Архивная игра исчезает из выбора нового этапа.
5. Можно создать пользовательскую игру с картинкой.
6. Можно создать её прямо из программы и сразу добавить этап.
7. Можно посмотреть полный паспорт.
8. Пользовательскую игру можно дублировать.
9. Редактирование создаёт новую версию и не меняет старые этапы.
10. Экспорт / импорт версии 0.2 переносит библиотеку вместе с мероприятием.
11. Старая версия 0.1 продолжает импортироваться.
12. Готовая сборка остаётся автономным HTML-файлом.
