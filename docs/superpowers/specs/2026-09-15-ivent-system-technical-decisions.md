# IVENT SYSTEM – технические решения

Дата: 2026-09-15
Статус: нормативное дополнение к архитектурной спецификации
Связанный документ: `docs/superpowers/specs/2026-09-15-ivent-system-design.md`

## 1. Цель документа

Этот документ фиксирует технологические решения, которые архитектурная спецификация намеренно оставляла на уровне принципов. Все решения ниже обязательны для первого цикла реализации, пока отдельное архитектурное решение явно их не заменит.

## 2. Технологический набор

### Язык

TypeScript (типизированный JavaScript, дословно «типизированный язык сценариев») используется для всей прикладной логики.

Причины:

- строгие типы для состояния мероприятия, команд, событий и игровых модулей;
- безопаснее миграции сохранений;
- проще поддерживать контракты между модулями;
- меньше риск случайно сломать структуру данных при дальнейшем росте проекта.

### Интерфейс

React (библиотека пользовательских интерфейсов, название собственное) используется для интерфейса ведущего.

Причины:

- интерфейс состоит из большого количества зависимых состояний;
- требуется удобное разделение экранов и компонентов;
- библиотека достаточно зрелая для дальнейшего перехода к нескольким экранам и подключению телефонов.

В первой версии не подключается отдельная библиотека управления глобальным состоянием. Состояние ядра управляется собственным хранилищем и передаётся интерфейсу через тонкий адаптер. Это сохраняет игровое ядро независимым от React.

### Сборка

Vite (инструмент сборки, название собственное) используется как среда разработки и сборки.

Финальная пользовательская сборка обязана превращаться в один автономный HTML-файл. Для этого используется совместимый механизм встраивания JavaScript и CSS внутрь HTML, например `vite-plugin-singlefile` (дополнение Vite для одного файла, дословно «дополнение одного файла»), либо эквивалентный небольшой собственный этап сборки.

Конкретный механизм выбирается по результату: итоговый файл должен корректно запускаться локально через `file://` двойным щелчком.

### Тесты

Vitest (средство запуска тестов, название собственное) используется для модульных и сценарных тестов.

Для интерфейсных проверок на первом этапе достаточно тестов компонентов и ручной проверки контрольных разрешений. Автоматизация браузерных сценариев добавляется, когда основной поток интерфейса стабилизирован.

## 3. Правило версий зависимостей

При инициализации проекта используются актуальные стабильные версии зависимостей на дату реализации.

После первого успешного полного набора тестов версии фиксируются файлом блокировки зависимостей. Автоматическое обновление основных версий запрещено до отдельного решения.

## 5. Граница ядра

Папка `core` (ядро, дословно «ядро») не импортирует React, браузерный интерфейс, конкретные игры или конкретного поставщика ИИ.

Ядро принимает команду и текущее состояние, затем возвращает новое состояние и созданные события.

Концептуально:

```text
execute(state, command) -> { state, events }
```

Эта функция должна быть максимально чистой и детерминированной.

Побочные действия, включая сохранение, загрузку файлов, таймер реального времени и запросы к ИИ, находятся за пределами вычислительного ядра.

## 6. Модель изменения состояния

Состояние изменяется только через зарегистрированные команды.

Запрещено:

- менять баланс напрямую из компонента интерфейса;
- менять инвентарь напрямую из игрового модуля;
- изменять этап обходным способом;
- записывать в локальное хранилище из доменного модуля.

Разрешённый поток:

```text
Интерфейс / игра
      ↓
   команда
      ↓
валидация ядра
      ↓
новое состояние + события
      ↓
побочные эффекты
      ↓
сохранение + интерфейс
```

## 7. Случайность

Для всех игровых случайных операций используется собственный генератор псевдослучайных значений с сохраняемым `seed` (начальным значением, дословно «семя»).

`Math.random()` напрямую в доменной и игровой логике запрещён.

Это требуется для:

- воспроизводимых тестов;
- восстановления после ошибки;
- расследования спорной игровой ситуации;
- будущего повторного воспроизведения вечера.

## 8. Идентификаторы

Идентификаторы сущностей создаются через один общий генератор.

Требования:

- уникальны в рамках мероприятия;
- остаются стабильными после сохранения и загрузки;
- не зависят от отображаемого имени;
- пригодны для импорта и объединения данных в будущих версиях.

## 9. Время

В состоянии этапа не хранится постоянно уменьшающееся значение таймера.

Хранятся:

- запланированная длительность;
- момент запуска;
- накопленное прошедшее время до паузы;
- состояние паузы.

Отображаемое оставшееся время вычисляется интерфейсом. Такой подход предотвращает рассинхронизацию таймера после перезагрузки страницы.

## 10. Сохранение

Используется `localStorage` (локальное хранилище браузера, дословно «локальное хранилище») для первой версии.

Для каждой из трёх ячеек создаются отдельные ключи:

- основное состояние;
- резервное состояние;
- метаданные.

Перед записью нового основного состояния последнее валидное состояние переносится в резервное.

Если браузер сообщает об ошибке записи, интерфейс показывает явное предупреждение и предлагает немедленный экспорт JSON.

Резервная копия в том же `localStorage` защищает от логической порчи данных, но не считается защитой от полной потери хранилища браузера. Поэтому экспорт файла остаётся отдельным уровнем защиты.

## 11. Контроль целостности

Вместе с сохранением хранится контрольное значение сериализованных данных.

Цель первой версии – обнаружить случайную порчу или неполную запись, а не обеспечить криптографическую защиту от намеренного изменения файла.

## 12. Отмена

Отмена реализуется через сохранённую обратную команду или достаточный снимок изменённой части состояния.

Полный снимок всего приложения после каждого действия не является основным механизмом отмены, чтобы журнал оставался понятным и масштабируемым.

После отмены создаётся отдельное событие `ACTION_UNDONE` (действие отменено, дословно «действие отменено»), а исходная запись журнала сохраняется.

## 13. Игровые модули

Игровой модуль не получает прямой изменяемый объект глобального состояния.

Он получает:

- безопасный снимок нужного контекста;
- собственное локальное состояние;
- функцию отправки разрешённых команд ядру.

Классические игры первой версии являются сценарными модулями. Их физическая механика остаётся за столом, а программа управляет этапом, временем, результатами и наградами.

Аукцион является первой игрой, чья внутренняя механика целиком находится в приложении.

## 14. ИИ-адаптер

Контракт ИИ остаётся асинхронным и отделённым от ядра.

Ядро никогда не ожидает сетевой запрос внутри функции изменения состояния.

Поток:

```text
игровой модуль
  ↓
запрос способности ИИ
  ↓
адаптер поставщика
  ↓
результат / ошибка
  ↓
команда ядру
```

Это позволяет полностью запускать версию 0.1 без ключей доступа и подключения к сети.

## 15. Интерфейс

Для первой версии принимается компьютерный формат с основным целевым разрешением 1920×1080 и обязательной проверкой 1280×720.

Интерфейс строится по принципу одного главного рабочего экрана ведущего и полноэкранных режимов отдельных игр.

Основные действия должны выполняться максимум за 2–3 нажатия.

Модальные окна применяются только для операций с высокой ценой ошибки или для короткого ввода параметров.

## 16. Стили

Стили хранятся внутри проекта и попадают в итоговый HTML-файл при сборке.

Первая версия не зависит от внешней сети для шрифтов, иконок или таблиц стилей.

Иконки либо встраиваются как SVG, либо создаются средствами CSS.

## 17. Доступность без сети

После сборки версия 0.1 обязана:

- запускаться без интернета;
- показывать все базовые элементы интерфейса;
- поддерживать все классические игры;
- поддерживать экономику, магазин и аукцион;
- сохраняться и загружаться;
- импортировать и экспортировать файл состояния.

Функции, требующие ИИ, в будущих версиях обозначаются отдельно и не блокируют основной сценарий.

## 18. Минимальные команды проекта

После инициализации проекта должны существовать команды для:

- запуска среды разработки;
- сборки;
- запуска тестов;
- запуска тестов один раз для автоматической проверки.

Точные имена команд фиксируются в `package.json` (описание пакета проекта, дословно «пакет JSON») и в README (файл описания, дословно «прочитай меня») после создания каркаса.

## 19. Критерий технологической готовности каркаса

Каркас считается готовым, когда одновременно выполнены условия:

1. проект устанавливается из чистого состояния;
2. среда разработки запускается одной командой;
3. тесты запускаются одной командой;
4. финальная сборка создаёт один HTML-файл;
5. этот файл открывается напрямую в браузере;
6. базовый тест ядра проходит;
7. в исходном коде уже соблюдены границы `core`, `domain`, `games`, `storage` и `app`;
8. README содержит минимальную инструкцию запуска и сборки.

## 20. Решение по сложности

Для версии 0.1 запрещено добавлять инфраструктуру, которая не нужна текущему пользовательскому сценарию.

В частности, до отдельного решения не добавляются:

- сервер;
- контейнеризация;
- база данных;
- авторизация;
- маршрутизация для большого сайта;
- система плагинов общего назначения;
- сложный фреймворк управления состоянием;
- микросервисная архитектура.

Основной приоритет – надёжный автономный игровой артефакт и простота дальнейшего добавления мини-игр.
